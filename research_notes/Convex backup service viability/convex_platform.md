# Convex Cloud platform: backup, keys, pricing, and adoption (as of 8 October 2026)

Research date: 8 October 2026. Pages below were fetched that day unless a source carries its own date. Older company claims are dated in the finding.

Official docs are marked **[official]**. Company marketing and press are **[company claim]**. Open-source backend code is **[source]**. Third-party writeups, Discord, and feature requests are **[community]**. Aggregator pricing sites are **[aggregator]** and are not treated as authoritative where they disagree with Convex pages.

## What does Convex officially provide for backups, snapshots, exports, imports, and point-in-time recovery in 2026? Is backup a paid add-on, included, or missing?

### Takeaway
Convex Cloud has first-party logical snapshot backup and restore in the dashboard and via `npx convex export` / `npx convex import`. Manual snapshots exist on Free/Starter with tight retention; automatic daily or weekly snapshots require Professional or above and are a listed plan feature, not a separate backup SKU. Dedicated deployments add non-downloadable physical backups. Point-in-time recovery is not a documented product; a June 2026 feature request is still open.

### Cited Findings
- **[official]** “Convex supports Backup & Restore of data via the dashboard.” “A backup is a consistent snapshot of your table data made at the time of your request. Backups can be configured to include file storage.” Manual backup: “Backup Now”; “may take a few seconds to a few hours.” “Manual backups are stored for 7 days.” “Deployment configuration and other data (code, environment variables, scheduled functions, etc.) will not be included.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Periodic backups: check “Backup automatically”; daily or weekly; choose time of day / day of week and whether to include file storage. “Daily backups are stored for 7 days. Weekly backups are stored for 14 days.” “Periodic backups require a Convex Pro plan.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Restore is in-dashboard (“Restore” on a backup). Same deployment or another deployment on the same team via the deployment selector. “Restores may take a few seconds to a few hours.” “restoring is a destructive operation that wipes your existing data and replaces it with that from the backup.” Recommended extra backup before restore. “Existing files in the deployment will not be deleted when restoring from a backup, but any files in the backup that do not currently exist in the deployment will be uploaded.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Emergency restore checklist on the same page: extra backup first; restore data; `npx convex dev` to push known-good code; `npx convex env` or dashboard for env vars; dashboard or mutations for manual data fixes. Code and env vars are outside the snapshot. — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Download from the dashboard, or “generate an export in the same format” with `npx convex export --path ~/Downloads`. ZIP name `snapshot_{ts}.zip` where `ts` is a UNIX timestamp in nanoseconds. Tables at `<table_name>/documents.jsonl`, one document per line. With file storage: `_storage` folder, metadata in `_storage/documents.jsonl`, each file under `_storage/`. “Downloaded ZIP files can be imported into the same deployment or a different deployment with the CLI.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** FAQ limitations: “Each backup is accessible for up to 7 days.” “On the Free/Starter plan, up to two backups can stored per deployment at a time. Deployments on Convex Professional plan can have many backups with standard usage based pricing.” (The “up to 7 days” sentence sits next to the earlier “weekly backups are stored for 14 days” sentence; both are on this page.) — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Pricing of backups: “Backups uses database bandwidth to read all documents, and file bandwidth to include user files. The generation and storage of the backup itself is billed with the same bandwidth and storage pricing as user file storage.” Usage shows in the usage dashboard. — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Snapshot contents gap, quoted: “The backup only contains the documents for your tables and files in file storage. In particular it lacks: 1. Your deployment's code and configuration. Convex functions, crons.ts, auth.config.js, schema.ts, etc. are configured in your source code. 2. Pending scheduled functions. You can access pending scheduled functions in the `_scheduled_functions` system table. 3. Environment variables. Environment variables can be copied from Settings in the Convex dashboard.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Dedicated hardware: “dedicated deployments (D1024 and D2048) have physical backups configured automatically for every 24 hours and accessible for up to 7 days. Physical backups are faster and cheaper due to the ability to leverage the dedicated database hardware, however restores require contacting Convex support. Physical backups cannot be downloaded. Cross-deployment restores are not supported into dedicated deployments. Physical backups are included in the price of dedicated hardware.” — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Limits page deployment classes: S16 and S256 “Backup/restore” = “Logical”; D1024 and D2048 = “High-speed physical”. Max dataset: S16/S256 1 TB, D1024 4 TB, D2048 8 TB. Classes by plan: Free/Starter S16; Professional S256; Business and Enterprise may choose S16, S256, D1024, or D2048. — [Limits](https://docs.convex.dev/production/state/limits)
- **[official]** Pricing comparison row “Daily backups”: Free & Starter No; Professional Yes; Business & Enterprise Yes. Row “Fast backup/restore”: Free & Starter No; Professional No; Business & Enterprise Yes. — [Choose Your Plan](https://www.convex.dev/pricing)
- **[official]** File storage limits note: storage “Includes user files and backups.” Data egress “Includes serving user files, accessing user files inside functions, and generating and restoring backups.” — [Limits](https://docs.convex.dev/production/state/limits)
- **[official]** CLI export: `npx convex export`; `--path` (directory or unoccupied `.zip`); `--include-file-storage` puts files in `_storage` inside the ZIP; `--prod` for the project’s default production deployment; `--deployment` accepts a deployment name, `dev/james`, `staging`, `dev`, `prod`, `local`, or `project-slug:reference` / `team-slug:project-slug:reference`. “By default, this exports from your dev deployment.” — [CLI export](https://docs.convex.dev/cli/reference/export)
- **[official]** Data export guide: zip export is “taking a backup and downloading it” or the same CLI command. Separate path: “programmatically do a paginated streaming export by using the Data Sync API or with an integration with a third party provider.” — [Data Export](https://docs.convex.dev/database/import-export/export)
- **[official]** Import of a backup ZIP: `npx convex import <path>.zip`. Documents keep `_id` and `_creationTime` “so references between tables are maintained.” Imports into tables that already have data fail unless `--replace`. Example: `npx convex import --prod --replace backup.zip`. File-storage ZIPs “import the files and preserve `_storage` documents, including their `_id`, `_creationTime`, and `contentType` fields.” “Data import uses database bandwidth to write all documents, and file bandwidth if the export includes file storage” (usage function name `_cli/import`). — [Data Import](https://docs.convex.dev/database/import-export/import)
- **[official]** Import caveats: “Avoid changing the ZIP file” between download and import; manual ZIP edits “may be possible, but remain undocumented.” “Data import is not always supported when importing into a deployment that was created before Convex version 1.7.” “you can always restore from backups from its own deployment.” Fivetran streaming export “does not handle data imports or backup restorations”; Convex recommends resetting that sync after a restore or import. — [Data Import](https://docs.convex.dev/database/import-export/import)
- **[official]** Overview page still says “Data Import & Export is currently a beta feature.” Export paths listed there: dashboard zip, or Fivetran continuous export. Import paths: CSV/JSON CLI, dashboard or CLI restore, Airbyte. This beta banner is absent from the Backup & Restore page fetched the same day. — [Data Import & Export](https://docs.convex.dev/database/import-export)
- **[official]** Streaming export (Fivetran) “requires a Convex Pro plan.” It is framed as continuous export for analytics, not as snapshot backup. Airbyte is the streaming import connector. — [Streaming import/export](https://docs.convex.dev/production/integrations/streaming-import-export)
- **[official]** Component table data “is included in snapshot imports and exports” (Stack article, Convex-published). — [Components for your Backend](https://stack.convex.dev/backend-components)
- **[community]** Point-in-time recovery is a feature request, not a shipped feature. Ship by Convex request “#363 Point in Time Recovery (PITR, Backups by Second)”, status “Requested”, submitted 11 June 2026. Author text: “a simple backup once a week won't cover a lot of possible issues” and asks to “go to any second in the history for the Deployment or at least the Database instance.” “Development Updates: No updates yet.” “Total backing 85 from 8 supporters.” — [Ship request #363](https://ship.convex.dev/requests/js7dggash7ddpw301ckdhaggp188fbkr)
- **[official]** No point-in-time recovery, continuous WAL, or second-level restore appears on the Backup & Restore page fetched 8 October 2026. The documented restore points are the snapshot ZIPs (and, on D1024/D2048, support-operated physical backups). — [Backup & Restore](https://docs.convex.dev/database/backup-restore)

### Inferences
- Backup is included as a product capability, with plan gates, not sold as a named add-on. Free/Starter can take and keep two manual logical snapshots for 7 days. Automatic daily/weekly snapshots are a Professional (and above) feature. “Fast” physical backup/restore is Business & Enterprise dedicated hardware, included in that hardware price, and is not a customer-downloadable archive.
- A third-party hosted backup cannot call the physical-backup path. Its workable Cloud API is the logical ZIP (`npx convex export` or a dashboard download), which the customer can also do themselves.
- The product gap versus Convex’s own backups is retention beyond 7 days (14 for weekly), storage outside Convex, customer-held encryption, cadence tighter than daily, and a copy that survives a Convex-account or Convex-region failure. It is not “Convex has no export.”
- The import-export overview’s “beta” label conflicts in tone with a fully written backup/restore guide. Treat the backup/restore and limits pages as the current product description, and treat the beta banner as possible doc drift until Convex removes it.

### Gaps
- No official page states a maximum ZIP size, a documented export timeout, or a customer-visible export rate limit (see the limits section).
- The 7-day FAQ line versus 14-day weekly retention is unresolved in the docs themselves.
- Whether system tables such as `_scheduled_functions` are inside the ZIP is not spelled out. The page both says pending scheduled functions are lacking and points at that system table.
- No public status-page URL was retrieved in this pass (no `status.convex.dev` result in the searches run).

## How do Convex deploy keys and admin keys work, and what is the blast radius if a backup vendor stores one?

### Takeaway
Cloud deploy keys are permission-scoped service tokens. A backup vendor only needs backup create/download (and file inclusion is a flag on export, not a separate documented permission). A full production deploy key or an admin key is complete deployment control, and admin keys are irrevocable secrets baked into the deployment. Issued deploy keys keep their original permissions after the creator’s role changes until the key is deleted.

### Cited Findings
- **[official]** `CONVEX_DEPLOY_KEY` makes the CLI non-interactive. “Deploy keys identify a deployment, project, or team; confer permission to take certain actions with those resources; and can change the behavior of the convex CLI.” Login instead stores a user token at `~/.convex/config.json` that “grants permission to push code to and read/write data from any deployment this user has access to.” — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Production deploy key example format: `prod:qualified-jaguar-123|eyJ2...0=`. “A production deploy key specifies the production deployment of a project and grants permissions to deploy code to it.” Used from Vercel, Netlify, Cloudflare build pipelines. Preview key format: `preview:team-slug:project-slug|eyJ2...0=`, changes `npx convex deploy` to a preview branch. — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Admin key: “An admin key provides complete control over a deployment.” Example format: `bold-hyena-681|01c2...c09c`. “Unlike other types of deploy key, an admin key does not require a network connection to https://convex.dev to be used since it's a irrevocable secret baked into the deployment when created.” Used for anonymous local backends; “rarely need to be set explicitly.” Setting `CONVEX_DEPLOY_KEY` to one targets that deployment. — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Project token: `project:team-slug:project-slug|eyJ2...0=`. “grants total control over a project” including creating dev and prod deployments. Obtained when a user grants a project to an organization via a Convex OAuth app. “Actions made with the token are on behalf of the user so if a user loses access to a project the token no longer grant access to it.” — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Dev deploy key: `dev:joyful-jaguar-123|eyJ2...0=`. “might be used to provide an agent full access to a single deployment for development. This can help limit the blast radius when developing with an agent.” — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Dashboard: deployment settings → Deploy keys → “Generate a deploy key”. “choose which actions it's allowed to perform.” CI example: enable `deployment:deploy` for `npx convex deploy`. “For CLI usage or AI agents, you may want to grant more permissions, such as viewing logs and reading/writing data or environment variables.” Delete from the deploy keys list. CLI alternative: `npx convex deployment token create <name>` and `delete`, only when logged in with a personal access token; “these commands cannot be invoked with a `CONVEX_DEPLOY_KEY` already in scope.” — [Deploy Keys](https://docs.convex.dev/cli/deploy-key-types)
- **[official]** Role-action model. On production, a Team Developer who is not also Project Admin “gets a read-only deployment identity.” Data-plane actions (quoted names and descriptions):
  - `deployment:deploy` — push code. Team Developer: non-prod only.
  - `deployment:pause`, `deployment:unpause`. Team Developer: non-prod only.
  - `deployment:logs:view`, `deployment:metrics:view`, `deployment:auditLog:view`. Team Developer: yes, including prod.
  - `deployment:env:view` — Team Developer yes. `deployment:env:write` — non-prod only.
  - `deployment:data:view` — “Read the deployment's database tables.” Team Developer yes. `deployment:data:write` — non-prod only.
  - `deployment:functions:runInternalMutations`, `deployment:functions:runInternalActions`, `deployment:functions:actAsUser` — non-prod only for Team Developer.
  - `deployment:delete` — delete a deployment. Team Developer: non-prod only.
  - Backups: `deployment:backups:view`, `deployment:backups:download` — “View and download deployment backups.” Team Admin, Team Developer, and Project Admin all yes.
  - `deployment:backups:create`, `deployment:backups:import`, `deployment:backups:delete` — “Create, restore, or delete backups.” Team Developer: non-prod only.
  - `deployment:backups:configurePeriodic`, `deployment:backups:disablePeriodic` — Team Developer: non-prod only.
  — [Role Actions](https://docs.convex.dev/team-management/role-actions)
- **[official]** “Deploy keys and preview deploy keys are service tokens. Once issued, they carry their own permissions independent of the creator's current role: if a team member has already created a deploy key or preview deploy key, that key continues to work with its original permissions even if the member's team role or custom role later changes. To revoke a key's access, delete the key from the deployment or project settings page.” Team access tokens are different: they “can only perform actions its creator is allowed to perform” and do not escalate. — [Role Actions](https://docs.convex.dev/team-management/role-actions)
- **[official]** Fivetran streaming export key: enable `deployment:data:view` “so the connector can read the documents in your tables and their schema.” Airbyte import key: enable `deployment:backups:import` “so the connector can write imported data into your deployment.” — [Streaming import/export](https://docs.convex.dev/production/integrations/streaming-import-export)
- **[source]** Open-source backend commit “Migrate more endpoints to operation-based permission checks (#49541)” maps snapshot export request to `DeploymentOp::CreateBackups` (replacing a blanket admin check) and snapshot import upload to `DeploymentOp::ImportBackups`. The public docs’ matching action names are `deployment:backups:create` and `deployment:backups:import`. This is backend source, not a Cloud docs sentence that “`npx convex export` requires exactly these permissions.” — [commit 834b7d4](https://github.com/get-convex/convex-backend/commit/834b7d4f49d92dc26d39b0dcf9c93feb9d57274f)
- **[source]** CLI helper `startSnapshotExport` POSTs `/api/export/request/zip?includeStorage=` with the deployment credential the CLI calls `adminKey`, then polls `_system/cli/exports:getLatest`. The word adminKey in that file is the CLI’s credential parameter, not proof that only legacy admin keys work. — [convexExport.ts](https://github.com/get-convex/convex-backend/blob/88a2a911/npm-packages/convex/src/cli/lib/convexExport.ts)

### Inferences
- Blast radius is whatever actions were checked when the key was minted, and it does not shrink if the employee who minted it is later demoted. Revocation is delete-the-key, not role change.
- Minimum key for a backup vendor, if Cloud matches the open-source operation map: `deployment:backups:create` to start an export, plus `deployment:backups:download` if the vendor downloads an existing dashboard backup. `--include-file-storage` pulls user files into that same ZIP; docs do not list a separate file-storage permission. That key can read all table documents (and files, if the flag is on). It should not, by itself, deploy code, write rows, change env vars, pause the deployment, or run a destructive import.
- A customer who pastes a normal CI production deploy key (`deployment:deploy` only) may not be enough to export. A customer who pastes an old “full” production key, a dev key described as “full access,” a project token, or an admin key gives the vendor write, deploy, and possibly delete. Admin keys cannot be revoked by calling convex.dev; docs call them irrevocable and baked in. Those are the wrong credential for a hosted backup.
- `deployment:backups:import` is a restore/write permission. A backup product that also offers one-click restore into production is a different, larger blast radius than export-only: `--replace` “wipes your existing data.”
- Team Developer cannot create or import backups on production unless they are also Project Admin. A vendor key is not subject to that role gate after issuance; the key’s own permission list is.

### Gaps
- Cloud docs do not publish a one-line “export requires these checkboxes” guide. The CreateBackups mapping is from open-source backend code at a specific commit, not a Cloud changelog.
- No official doc states whether a key with only `deployment:data:view` can call `npx convex export`. Fivetran uses `data:view` for streaming read, which is a different API.
- No official doc states whether deploy keys can delete files, empty tables, or read env vars unless those actions were granted (`deployment:data:write`, `deployment:env:view`).
- Token lifetime, rotation requirements, and IP allowlists for deploy keys were not found.

## What are the documented limits on `npx convex export` / snapshot export?

### Takeaway
Official docs document format, optional file storage, duration “seconds to hours,” plan retention caps, and bandwidth/storage billing. They do not document a max ZIP size, a rate limit, a timeout, or a minimum interval. Open-source backend code allows only one requested or in-progress export at a time. That concurrency rule is source code, not a Cloud SLA page.

### Cited Findings
- **[official]** Export commands and flags are only `--path`, `--include-file-storage`, `--prod`, and `--deployment`. No rate-limit, size, or timeout flags are listed. — [CLI export](https://docs.convex.dev/cli/reference/export)
- **[official]** Dashboard backup “may take a few seconds to a few hours, depending on how much data is in your deployment.” Same range for restore. — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Free/Starter: at most two stored backups per deployment. Professional: “many backups with standard usage based pricing.” Manual retention 7 days; daily 7 days; weekly 14 days; FAQ also says each backup is accessible for up to 7 days. — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Billing: database bandwidth to read all documents; file bandwidth to include user files; backup bytes billed as file storage. File storage prices (US, other regions 1.3× unless noted): Free hard cap 1 GB storage and 1 GB/month egress; Starter 1 GB and 1 GB/month included then $0.033/GB-month storage and $0.132/GB egress; Professional 100 GB and 50 GB/month included then $0.03/GB-month and $0.12/GB; Business and Enterprise $0.03/GB-month and $0.12/GB. Egress includes “generating and restoring backups.” Database storage explicitly “not files or backups.” — [Limits](https://docs.convex.dev/production/state/limits), [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** Periodic schedule options documented: daily or weekly, not hourly. — [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[official]** File storage in the ZIP is opt-in (`--include-file-storage` or the dashboard include-file-storage choice). Without it, the ZIP is table documents only. — [CLI export](https://docs.convex.dev/cli/reference/export), [Backup & Restore](https://docs.convex.dev/database/backup-restore)
- **[source]** Export worker: “Can only have one export requested or in progress at once.” Interrupted in-progress exports are restarted. This is `crates/application/src/exports/worker.rs` in `get-convex/convex-backend`. — [worker.rs](https://github.com/get-convex/convex-backend/blob/88a2a911/crates/application/src/exports/worker.rs)
- **[community / third-party]** Octopus Deploy’s “Convex - Export Data” step sets its own command timeout default to 600 seconds and says “Large datasets may require a higher value.” That default is the integration’s, not a Convex-documented limit. The step runs `npx convex export` with a deploy key before a production deployment. — [Octopus Convex export](https://octopus.com/integrations/convex/convex-export-data)
- **[community]** GitHub issue on self-hosted Convex (not Convex Cloud): snapshot export with storage against Cloudflare R2 as the self-hosted storage backend fails with S3 `InvalidPart` (“All non-trailing parts must have the same length”), retries forever; author also says large exports with `includeStorage=false` can fail. This is about Convex’s own object storage when self-hosting, not about a Cloud customer uploading an export ZIP to R2. — [convex-backend issue #395](https://github.com/get-convex/convex-backend/issues/395)

### Inferences
- A hosted service can schedule `npx convex export` more often than Convex’s daily/weekly checkbox, but each run re-reads the database and, with files, re-downloads file bytes. On Professional, included egress is 50 GB/month and included file storage is 100 GB; backup objects count toward file storage while they live on Convex, and generating them counts toward egress. Daily full file exports of a large deployment can cost more than the $25/developer seat.
- Free-plan customers who export often still only keep two Convex-side copies, but CLI exports downloaded off-platform are the customer’s copies. The two-backup cap is about backups stored in Convex, as written.
- Do not assume Cloud will accept overlapping exports. The open-source worker rejects a second requested/in-progress export. If Cloud uses that worker, a vendor must serialize exports per deployment.

### Gaps
- No official max snapshot size, timeout, HTTP status for “export already running,” or “how many exports per day” number was found.
- Whether Cloud dashboard periodic backups and a simultaneous CLI export share the one-at-a-time lock was not confirmed in docs.
- Cloud export behavior for multi-terabyte dedicated datasets (max dataset 4 TB / 8 TB) is not quantified beyond “a few seconds to a few hours” and “contact support” for physical restore.

## How is Convex priced, and does that imply a buyer who would pay extra for backups?

### Takeaway
Self-serve list price is Free/Starter at $0 plus usage, Professional at $25 per developer per month, and Business at a $2,500 monthly minimum. Daily logical backups are a Professional feature already in that $25 seat. Buyers who might still pay are those who need retention past 7–14 days, off-Convex copies, or a cadence Convex does not schedule. Business/Enterprise already get support-operated physical backups on dedicated hosts and are a smaller, higher-touch set.

### Inferences
- The paying self-serve buyer is a Professional team at $25 per developer (cap 20) who already gets daily logical backups inside Convex for 7 days. An extra hosted backup is a second system. ### Gaps
