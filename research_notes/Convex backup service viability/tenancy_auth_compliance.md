# Tenancy, authentication, secret custody, and compliance for a hosted Convex backup service

Scope is the control plane that would store customer Convex deploy keys and full database archives, plus the option to write archives only to customer-owned R2/S3, and an agency operator who manages many client projects. Notes distinguish **code in this repository as of this reading** from **industry practice recommended for a hosted service**. The open-source self-hosted product is a non-goal to abandon: hosted tenancy is a second operating mode, not a replacement for the single-install product.

Primary local sources: [docs/PRODUCT_SPEC.md](../../../docs/PRODUCT_SPEC.md), [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md), [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md), [docs/API_CONTRACT.md](../../../docs/API_CONTRACT.md), [crates/core/src/db.rs](../../../crates/core/src/db.rs), [crates/core/src/auth.rs](../../../crates/core/src/auth.rs), [crates/core/src/secrets.rs](../../../crates/core/src/secrets.rs), [crates/server/src/lib.rs](../../../crates/server/src/lib.rs), [crates/core/src/convex.rs](../../../crates/core/src/convex.rs), [crates/core/src/restore.rs](../../../crates/core/src/restore.rs).

## What tenancy model fits this schema, and what breaks in SQLite plus one master key?

### Takeaway
Use one shared application database with a real tenant id and row-scoped authorization for the early hosted service. Keep the self-hosted binary as a single-tenant install of the same domain model. Schema-per-tenant and deployment-per-customer are later isolation upgrades, not the first hosted shape. The current SQLite schema cannot do that safely: teams exist, but users, secrets, jobs, runs, and audit rows are global, every list query is unscoped, and one install-wide key decrypts every secret.

### Cited Findings
- Operating a hosted SaaS is an explicit product non-goal today. Audiences already include solo developers, agencies with many client deployments, and teams that want roles and audit trails. — [docs/PRODUCT_SPEC.md](../../../docs/PRODUCT_SPEC.md)
- The live app database is SQLite. The schema stores users, API tokens, encrypted secrets, teams, projects, targets, destinations, jobs, schedules, and backup runs. Postgres is described as a scale-out target and is not the active code path. — [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md)
- `teams` and `projects.team_id` and `destinations.team_id` exist. `users`, `api_tokens`, `secrets`, `targets`, `jobs`, `runs`, `schedules`, and `audit_events` have no tenant or team column. Migration inserts a single team named "Default" when none exists, and `default_team_id()` returns `SELECT id FROM teams LIMIT 1`. New projects and destinations are written against that default team. — [crates/core/src/db.rs](../../../crates/core/src/db.rs), [crates/core/src/db/resources.rs](../../../crates/core/src/db/resources.rs)
- List functions for projects, targets, destinations, jobs, runs, schedules, users, tokens, secrets, and audit events select the whole table. They do not filter by team or user. — [crates/core/src/db.rs](../../../crates/core/src/db.rs), [crates/core/src/db/resources.rs](../../../crates/core/src/db/resources.rs), [crates/core/src/auth.rs](../../../crates/core/src/auth.rs), [crates/core/src/secrets.rs](../../../crates/core/src/secrets.rs)
- OWASP’s multi-tenant cheat sheet lists three database strategies: separate databases (credential and backup boundary, higher operational cost), separate schemas (needs disciplined grants and `search_path` handling), and shared tables with a row boundary (needs enforceable tenant ownership, policy coverage, a constrained request role, and negative-path tests). It says client-supplied tenant ids are selectors only and must be checked against the authenticated principal’s membership. — [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
- The same cheat sheet’s Postgres row-level security pattern is `tenant_id = current_setting('app.current_tenant')`, with `FORCE ROW LEVEL SECURITY`. Superuser and `BYPASSRLS` roles always bypass it. A normal `SET` survives connection reuse; `SET LOCAL` / `set_config(..., true)` is transaction-local. Missing tenant context should fail closed. — [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
- ASVS requirement 4.1.6 (Level 1) requires data-specific access restricted to consumers with explicit permission, specifically to mitigate IDOR and broken object-level authorization. A separate multi-tenant requirement, 4.3.4, says consumer operations must never affect tenants the consumer is not allowed to touch; OWASP discussion placed that requirement at Level 2 because it is extra work beyond ordinary object authorization, and commenters treated a miss as a mass-data-loss event. — [OWASP ASVS issue 2716](https://github.com/OWASP/ASVS/issues/2716), [OWASP ASVS issue 2693](https://github.com/OWASP/ASVS/issues/2693)

### Inferences
- **Early hosted recommendation: shared Postgres tables with `tenant_id` on every customer-owned row, membership checked in the request, and Postgres RLS as a backstop.** The schema already points this way (`teams` → projects and destinations). Agencies map to one tenant (the agency account) plus a client/project boundary inside it, not to a separate database per client. Customer-owned R2/S3 is a storage destination attribute on that same control plane, not a different tenancy model.
- **What the current design breaks if you only “add a hosted flag”:**
  - One SQLite file and one master key are an install boundary. Every customer who shares that file shares decryption of every deploy key.
  - Users are not members of teams. Roles (`owner`, `admin`, `operator`, `viewer`) are global to the install. An agency client cannot be isolated from another client, and a customer cannot be isolated from the operator’s other customers.
  - Secrets have no owner. `get_secret(id)` decrypts by id alone.
  - Unscoped `SELECT`s mean the first missed `WHERE` is a cross-tenant read. SQLite has no equivalent of the Postgres RLS backstop OWASP describes.
  - A single worker process decrypts whatever secret the job references. There is no per-tenant data plane.
- **Schema-per-tenant** fits a later regulated tier (separate DB role and migration stream per customer) and fights the current “one Default team” code. **Deployment-per-customer** (one self-hosted process and master key per customer) is the strongest early isolation and matches today’s security boundary, but it is an operations product, not a multi-tenant service: upgrades, scheduling, and agency login across clients all become N installs.
- **Do not throw away the self-hosted product.** Keep single-tenant SQLite as the open-source mode. Hosted mode should be a build that adds tenancy, Postgres, and a key hierarchy. Customers who will not accept operator custody can keep running the existing binary.
- **“Build tenancy properly later” cost:** every table and query grows a tenant predicate; archives and secrets must be backfilled with an owner; a single-key vault must be decrypted and re-wrapped under per-tenant keys; tests must prove negative paths. Doing this after customer data exists is a migration of production secrets and full database archives, not a schema tweak. RLS added after the app role is a superuser does not isolate anything, per the OWASP warning on `BYPASSRLS`.

### Gaps
- No measurement in this repo of SQLite write contention or of a Postgres migration design. The architecture doc names Postgres as a future target and does not specify RLS, pooling, or a tenant column plan.
- No sourced cost comparison of schema-per-tenant versus shared-table operations for a backup product specifically.

## What authentication is table stakes for a paid hosted version, and what is premature?

### Takeaway
Ship email and password, expiring browser sessions, revocable API tokens, and MFA for anyone who can read secrets or start a restore. Magic link can replace passwords for humans; enterprise SSO and SCIM are premature until a buyer’s procurement requires them. The repo already has Argon2 passwords, four global roles, and bearer tokens, but it does not have sessions, expiry, MFA, or a user-to-tenant membership.

### Cited Findings
- Documented auth: first-run owner bootstrap, browser sessions, API bearer tokens, roles owner/admin/operator/viewer. Bootstrap is supposed to return a one-time API token. Login is specified as email/password returning a revocable API token. Mutating browser calls are specified to need CSRF/session protection or a bearer token. Scoped token permissions are listed as a future resource group. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md), [docs/API_CONTRACT.md](../../../docs/API_CONTRACT.md)
- Implemented auth differs from that document. `POST /api/v1/login` verifies the password and inserts a new API token named `web-login` on every success. `require_role` accepts only `Authorization: Bearer`. No cookie, CSRF, Origin, or session code exists under `crates/server`. Tokens are stored as SHA-256 hex, compared in constant time, and can be revoked, but the table has no expiry column. Each login therefore leaves another live bearer credential. — [crates/server/src/lib.rs](../../../crates/server/src/lib.rs), [crates/core/src/auth.rs](../../../crates/core/src/auth.rs), [crates/core/src/db.rs](../../../crates/core/src/db.rs)
- Passwords require an `@` in the email and at least 12 characters, and are stored with Argon2 (default parameters) and a random salt. Roles are global: owner and admin can manage, operator can run backups, viewer is read-only. There is no per-team role. — [crates/core/src/auth.rs](../../../crates/core/src/auth.rs)
- API tokens are 32 random bytes prefixed `cab_`. The raw value is returned once. Listing tokens returns metadata only. — [crates/core/src/auth.rs](../../../crates/core/src/auth.rs)
- OWASP ASVS session principles: sessions unique per individual, not guessable or shared, invalidated when no longer required, and timed out on inactivity. ASVS 3.7.1 (Level 1) requires a full valid login session, or re-authentication or secondary verification, before sensitive transactions or account modifications. — [OWASP ASVS V3](https://github.com/OWASP/ASVS/blob/master/4.0/en/0x12-V3-Session-management.md)
- OWASP multi-tenant guidance: bind tenant context to a server-verified identity and current membership; do not let a header or body tenant id authorize itself. — [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)

### Inferences
- **Table stakes before taking money for hosted custody:**
  - Verified email, password reset, and login rate limiting. None of these exist in the server routes read here.
  - Real browser sessions: httpOnly, Secure, SameSite cookies, server-side expiry and revocation, CSRF on cookie-authenticated mutations. The documented CSRF rule is not implemented; today’s UI token is a long-lived bearer minted at login.
  - Token expiry, last-used time, and scopes. The API contract already calls scoped tokens a future item. A backup agent token should not be allowed to restore.
  - MFA (TOTP or WebAuthn) for owners and anyone who can create tokens, read secret-use paths, or restore. ASVS 3.7.1 is the control: re-auth or a second factor before restore and before revealing or rotating a deploy key.
  - Membership: user belongs to a tenant, with a role inside that tenant. Agency staff get explicit project grants. Operator employees are a separate break-glass role, not a row in the customer’s user table.
  - Audit that records the authenticated user. Current `record_audit` calls in user and token creation pass the actor `"system"`.
- **Acceptable, not required on day one:** magic-link login as a password alternative; Google or GitHub OAuth for solo developers. OAuth does not solve tenancy.
- **Premature until a specific buyer asks:** SAML/OIDC enterprise SSO, SCIM provisioning, and per-customer IdP. Those matter when an agency or mid-market security review says “SSO required.” Building them before tenant membership exists ties identities to the wrong boundary.
- **Keep self-hosted auth as it is, with the session bug fixed upstream if the UI depends on it.** A local install’s first-run owner bootstrap is still the right open-source flow. Hosted signup is a different flow: public registration, billing identity, and no unauthenticated bootstrap once any user exists (bootstrap already closes after the first user, which is correct for one install and wrong as a hosted signup gate).

### Gaps
- No independent 2026 buyer survey was retrieved on how often sub-50-person SaaS customers require SSO versus MFA. The split above is inferred from ASVS and from the procurement pattern in the SOC 2 sources, not from a login-method census.
- Password-reset and email-deliverability vendors were not researched.

## How should per-tenant secret encryption work if the operator is willing to custody keys?

### Takeaway
The honest minimum is envelope encryption: a unique data key per tenant (or per secret), wrapped by a KMS key the application cannot export, with the tenant id bound into the encryption context. The current code is one SHA-256-derived AES-256-GCM key for every secret in the install. That is reasonable for a self-hosted operator who holds `CONVEX_AUTOBACKUP_MASTER_KEY`. It is not an honest hosted design, because a copy of the database plus that one environment variable decrypts every customer’s deploy key and storage credential.

### Cited Findings
- Deploy keys, self-hosted admin keys, S3 credentials, archive passphrases, webhook tokens, and API tokens are secrets. API responses return redacted metadata. Docker/headless installs use encrypted database storage. Native OS keychain is a target, not the hosted path. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md), [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md)
- `SecretVault::with_master_key` sets the AES-256-GCM key to `SHA-256(master_key string)`. Each secret stores a random 12-byte nonce and ciphertext. `from_env` requires `CONVEX_AUTOBACKUP_MASTER_KEY`. There is no per-secret or per-team key, no KMS, and no key id column. — [crates/core/src/secrets.rs](../../../crates/core/src/secrets.rs)
- During backup the worker decrypts the deploy key and passes it to the Convex process as `CONVEX_DEPLOY_KEY`. The same pattern is used for the read-only connection check. — [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md), [crates/core/src/convex.rs](../../../crates/core/src/convex.rs)
- Archive encryption is optional, per destination, age passphrase (scrypt). The passphrase lives in the same encrypted vault. Manifests stay unencrypted and record mode, key reference, plaintext SHA-256, and stored SHA-256. Changing the passphrase creates a new vault secret; older archives keep their original secret id. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md)
- AWS describes envelope encryption as: KMS generates a data key, the application encrypts data locally with that data key, and the data key is stored only in encrypted form under a KMS key. Direct KMS encrypt is limited to 4 KB, so archive bytes should not be sent to KMS. Decrypt requires permission on the KMS key. All use of the KMS key can be logged in CloudTrail. Encryption context is authenticated extra data: decrypt fails unless the same context is supplied. — [AWS KMS FAQ](https://aws.amazon.com/kms/faqs/), [GenerateDataKey](https://docs.aws.amazon.com/kms/latest/APIReference/API_GenerateDataKey.html)
- AWS Encryption SDK: a unique data key per message, encrypted under a wrapping key, stored with the ciphertext. Losing the wrapping key makes data unrecoverable. Specifying the wrapping key on decrypt is a stated best practice. Key commitment is recommended so a ciphertext decrypts to one plaintext. — [AWS Encryption SDK concepts](https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/concepts.html)
- AWS prescriptive guidance: separate identities for people who administer keys and people who use them; least privilege rather than `kms:*`; customer-managed keys when a choice exists. Encryption context must not contain secrets because CloudTrail stores it in plaintext. — [AWS Prescriptive Guidance, KMS](https://docs.aws.amazon.com/prescriptive-guidance/latest/encryption-best-practices/kms.html)
- NIST SP 800-53 Rev. 5 SC-12: establish and manage keys for generation, distribution, storage, access, and destruction under organization-defined requirements. Enhancement SC-12(6): maintain physical control of keys when an external provider encrypts stored information. SC-28: protect confidentiality and integrity of specified information at rest. SC-28(1): cryptographic mechanisms against unauthorized disclosure and modification. SC-28(3): protected storage for cryptographic keys, with a hardware-protected key store as the example. — [NIST SC-12](https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-12/), [NIST SC-28](https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-28/)
- A comparable backup vendor’s DPA (SimpleBackups) states logical separation between customer instances, encryption of sensitive authentication data at the database level, and database encryption at rest managed by AWS. That is a public description of operator custody, not a claim this repo does the same. — [SimpleBackups DPA](https://simplebackups.com/docs/getting-started/security-and-privacy/data-processing-agreement)

### Inferences
- **Minimum honest hosted design, given the founder accepts key custody:**
  1. One customer-managed KMS wrapping key for the service (hardware-backed). The application never sees the wrapping key bytes.
  2. A data key per tenant, or per secret if rotation must be finer. Store `wrapped_key` next to the ciphertext. Bind `tenant_id` (and secret id) as KMS encryption context so a wrapped key stolen from tenant A’s row cannot be unwrapped as tenant B.
  3. Decrypt the deploy key only inside the worker for the duration of the export, pass it via the environment to the child process as today, and drop it when the process exits. Do not log the child environment.
  4. Separate the IAM principal that runs backups (can `Decrypt` with that context) from the principal that administers the KMS key.
  5. Say in the security page: the operator can decrypt. Custody is the product. age passphrases stored in the same vault do not create a second party.
- **Customer-owned R2/S3 does not remove deploy-key custody.** The export still needs the plaintext deploy key in the worker. It does remove archive custody if the bucket policy lets the worker `PutObject` and the customer denies the operator `GetObject`. That split should be a named option, with a test that the operator’s control-plane credentials cannot read the object.
- **A stronger later option, not day one:** customer-held age identity or an external KMS key the operator cannot use without the customer. Scheduled backup and unattended restore then need a grant or an online unwrap, which is a different product. The existing age-passphrase feature is the self-hosted version of “archive encrypted before write,” and it stays valid there because the customer holds the master key.
- **“Add KMS later” cost:** every existing ciphertext was wrapped by SHA-256 of one string. Re-wrapping is a read-decrypt-rewrite of the secret table while backups are paused or dual-written. Archives encrypted with a vault passphrase must keep the old secret until those objects are re-encrypted or retired. If the master key and the SQLite file were ever backed up together, those copies remain a single compromise forever unless customers rotate deploy keys in Convex.

### Gaps
- Cloudflare’s key-management product was not needed to choose the model and was not fetched. R2 is already an S3-compatible destination in this repo; it does not wrap application secrets.
- No quote was retrieved for AWS KMS request pricing at a small tenant count. Cost is unlikely to dominate compared with archive storage; that is an inference, not a measured bill.

## What access isolation is required so one customer or agency client cannot read another’s key, archive, or restore into another deployment?

### Takeaway
Isolation has to hold on five paths: API reads, secret unwrap, object storage, the worker’s child process, and restore target selection. This repo enforces a global role and a typed confirmation phrase before restore. It does not bind a user to a team, a secret to a team, or a restore target to the archive’s owner. In a shared database that is a cross-tenant read and a cross-tenant restore.

### Cited Findings
- Authorization is specified as server-side for UI, API, CLI, and MCP. Owner has full control and destructive restore configuration; admin configures resources; operator runs backups, verification, restore drills, and reports; viewer reads. The UI is not an authorization boundary. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md)
- Implemented checks stop at `require_role`: any valid bearer token is “authenticated”; owner/admin can manage; owner/admin/operator can run backups. The handler then uses ids from the body or URL with no team comparison. — [crates/server/src/lib.rs](../../../crates/server/src/lib.rs)
- Restore requires the caller to resubmit the target deployment name and an exact safety phrase, and it refuses if verification failed. The check compares the typed deployment string to `target.deployment`. It does not check that the run’s job, the archive, and the destination target belong to the same team, because there is only one install-wide team in practice. — [crates/core/src/restore.rs](../../../crates/core/src/restore.rs)
- Destructive restore is specified as disabled for MCP by default. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md)
- OWASP: cross-tenant data leakage, tenant impersonation, IDOR, shared-cache and shared-queue poisoning, and incomplete offboarding are the named risks. Cache keys that vary by tenant must include the tenant id. Authorize before reading a cached protected value. Offboarding must remove residual access and honor retention. — [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
- NIST AC-4 (information flow enforcement) is a related control cited from SC-28’s related-controls list: rules for how information moves between components, separate from encryption at rest. — [NIST SC-28](https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-28/)

### Inferences
- **Required controls for the hosted primary (operator stores keys and archives):**
  - Every customer-owned row carries `tenant_id`. Agency clients are `project_id` (or a client id) inside the agency tenant. A second customer is a different `tenant_id`, not a different project in the default team.
  - Request middleware loads membership from the session, then every query includes that id. Postgres RLS is the backstop, using a non-owner, non-`BYPASSRLS` role. Admin support access is a separate, audited break-glass path, not a missing `WHERE`.
  - Secret unwrap is allowed only if the secret’s tenant matches the job’s tenant. KMS encryption context repeats that id so a swapped ciphertext blob fails closed.
  - Object keys are prefixed by tenant id. A destination’s credentials are stored as a secret of that same tenant. IAM or bucket policy for operator-hosted buckets denies listing outside the prefix. For customer-owned buckets, the worker receives only that destination’s credentials.
  - Restore target must be a deployment record in the same tenant as the archive. The existing confirmation phrase stays; it is a fat-finger control, not an authorization control. Cross-tenant restore is blocked even if the operator types the right deployment name.
  - Worker concurrency limits already exist globally and per target/destination. Add a per-tenant cap so one tenant cannot starve the queue (OWASP noisy-neighbor). The child process environment contains one deploy key; the temp restore directory is already unique per restore and should stay that way.
  - Delete-tenant deletes or returns secrets, revokes tokens, and applies the documented retention to archives, including customer buckets the operator can still delete. If the customer bucket denies delete, the contract says the customer must delete.
- **Agency mode:** one login, many clients, client-level isolation means project-scoped roles stored in a membership table. A viewer on client A who can guess client B’s target UUID must get 404. Global `Role::Admin` in this repo would see every client.
- **Self-hosted mode:** one team and one master key remain correct. Do not force RLS semantics into the single-user SQLite build beyond “the logged-in role can do what the role says.”

### Gaps
- Object-key layout was not fully traced. `storage_uri` is stored on the manifest and run copy; a tenant prefix convention for hosted buckets is a recommendation, not a description of current paths.
- No test in the files read proves a user in team A cannot pass team B’s id. There is no second team in the write path.

## What can be sold without SOC 2, when do questionnaires and GDPR show up, and what does “later” cost?

### Takeaway
SOC 2 is a procurement artifact, not the control that makes key custody safe. A tiny team can sell to developers and small agencies with an honest security page, a DPA, tenant isolation, and restore evidence. SIG Lite and shorter cloud questionnaires show up at SMB and mid-market vendor reviews; SIG Core and a SOC 2 Type II show up when the buyer treats production database archives as sensitive. GDPR applies as soon as EU personal data is in the archives on US servers, whether or not anyone has asked for SOC 2. Building the report later is a calendar of months plus a recurring cash cost; building isolation later is a data migration.

### Cited Findings
- AICPA: a Type I examination is as of a point in time and opines on suitability of design, not operating effectiveness. A Type II examination covers a specified period and includes tests of operating effectiveness. The guide does not set a universal minimum length for that period. — [AICPA SOC 2 guide excerpt, AAG-SOP](https://assets.ctfassets.net/rb9cdnjh59cm/2paxzm46AxmwDDSZGkdtFS/c01813c67d26de154898653c121a92ea/AAGSOP22E.pdf), [2017 Trust Services Criteria](https://assets.ctfassets.net/rb9cdnjh59cm/72xv4p67HVXKp6CjWmjkPk/1cdbfa19f6307e2720396b66a6194dc9/trust-services-criteria-updated-copyright.pdf)
- Practitioners say three months is the usual floor because shorter windows do not give a sample for monthly or quarterly controls, six months is a common first Type II, and twelve months is what many enterprise buyers eventually expect. They also say the three-month figure is convention, not an AICPA rule, and the engaged CPA firm must accept the window. — [TCSA, SOC 2 observation period](https://www.tcsa.in/learn/soc-2-observation-period), [Audit Suisse, Type I vs Type II](https://auditsuisse.com/soc-2-type-1-vs-type-2), [soc2auditors.org observation-period note](https://soc2auditors.org/insights/soc-2-observation-period-explained/)
- Vanta (vendor, selling the automation tool) says startups should budget $20,000 to $80,000+ all-in for year one; lean Security-only Type I sits at the low end. Vanta’s timeline: Type I in three to five months from a standing start, or 10–12 weeks if basic controls exist; Type II “adds an observation window (minimum of three month observation period)” and “a realistic timeline for a first Type 2 report [is] roughly four to six months.” Vanta says the sales pipeline is the usual trigger, and that procurement at large companies may pause onboarding until a report is on file. Vanta also claims “approximately 98% of Fortune 500 buyers and 85% of mid-market buyers require a Type 2 report.” That percentage is presented without a method on the page retrieved. — [Vanta, SOC 2 for startups](https://www.vanta.com/collection/soc-2/soc-2-for-startups)
- Viktar Patotski, 2026 founder-oriented writeup: small SaaS Type II year one $25k–$50k all-in; boutique Type II audit $12k–$30k and Type I $5k–$20k; platform list price cited from AWS Marketplace as Vanta Essentials $14,000/year (1–20 employees) and Drata Foundation $15,000/year (1–50); negotiated small-tier platform spend often $8k–$12k, list or a second framework $15k–$20k; pentest $5k–$15k if the auditor wants one; year two cash $15k–$30k. He treats SOC 2 as a subscription. — [Patotski, SOC 2 cost for startup SaaS, 2026](https://patotski.com/blog/soc-2-cost-for-startup-saas/)

The same page’s directory of listed fees (snapshot 21 August 2026, not prices paid) shows specialist CPA Type I $10,000–$35,000 and Type II $15,500–$50,000; full-service CPA Type II $30,000–$80,000; Big Four Type II $65,000–$200,000. Its planning table for a prepared 1–10 person Security-only team is first-year cash $10,000–$30,500 (audit $7,000–$10,000, platform $0–$9,500, pentest $3,000–$11,000) plus staff time valued at $25,000–$90,000 that is not in the cash total. Year-two cash for that profile is also $10,000–$30,500. The page says these are planning ranges, and that a platform’s own audit figures are marketing. — [soc2auditors.org, SOC 2 audit cost, October 2026](https://soc2auditors.org/soc-2-audit-cost/)

### Inferences
- **What can be sold with no SOC 2 report:** self-serve and founder-led deals where the buyer is a developer or a small agency and the security conversation is a call plus a written page. The page has to say: we hold deploy keys; we can decrypt; archives are (or are not) encrypted with keys we also hold; subprocessors and regions; how to delete a tenant; how restore is tested. A one-page DPA and a subprocessor list are the contract version of that page. A trust center that only says “SOC 2 in progress” is not a control.
- **When a questionnaire appears:** SIG Lite’s published audience is SMB and mid-market low-risk vendors. This product is a poor fit for “low-risk,” because the vendor holds production archives and a key that can export the live database. Expect a short custom security form or CAIQ-style cloud questions from smaller companies that have any vendor review, and SIG Core once the buyer has a security team and classifies the backup vendor as critical. That can be a 30-person customer, not only an enterprise. SOC 2 Type II becomes the substitute for answering those questionnaires, which is Vanta’s sales argument and matches how SIG/CAIQ are used. It does not appear on day one unless the founder chooses those buyers.
- **When SOC 2 starts to matter:** the first deal whose procurement checklist says “report or no vendor.” Type I can unblock a single deal if the buyer accepts a point-in-time design opinion; several 2026 sources disagree how often that still works (GRC Review says Type I is a reasonable first step for a 5-person company; YuSMP says Type I no longer closes mid-market; Vanta’s 98% figure is an unsourced vendor claim). Plan on Type II before a repeatable mid-market motion, not before the first ten design partners.
- **Rough tiny-team budget, October 2026, Security criterion only, one product:** cash commonly cited between about $10k and $50k in year one depending on whether the speaker counts only a cheap CPA plus a negotiated platform (soc2auditors.org prepared-team $10k–$30.5k; Patotski $25k–$50k; Vanta’s wide $20k–$80k+; YuSMP $50k–$120k once extra criteria and a large FTE are included). Audit-only specialist quotes are cited from about $7k–$10k (planning, small and ready) up to directory list bands of $15.5k–$50k. Year two does not go to zero: another examination plus the platform. Calendar: weeks to a few months to write policies and turn on evidence, then a Type I exam, or a Type II only after controls have run for a window the CPA will sign (conventionally 3, 6, or 12 months). A founder who starts the window before isolation and key custody exist will pay for a report that describes the wrong system, then pay again.
- **GDPR if EU customers put production data on US servers:** the customer is the controller of the personal data inside the Convex database; the hosted operator is the processor. Article 28 and 32 apply to that processing. Practical minimum before accepting EU production archives: a DPA, a subprocessor list (host, object storage, email, error tracking), encryption in transit and at rest, a retention period that actually deletes backup objects, a way to export or delete a tenant, and a transfer tool. SCCs are the durable tool. DPF certification is usable only while the July 2023 adequacy decision stands, and as of October 2026 that decision is in force and under active legal and political stress. Do not make DPF the only mechanism. Customer-owned EU buckets reduce the archive transfer; they do not remove the deploy key, which is also personal-data-adjacent credential material and still sits in the US control plane if the operator is in the US.
- **“Properly later” costs that are not the audit fee:** retrofitting tenant ids and RLS after customers exist; re-wrapping every secret under KMS; rotating customer deploy keys if the old master key was stored with the database; writing the policies SOC 2 will sample (access reviews, vendor list, incident response, restore tests) only when a deal forces it, which compresses the work into the sales cycle Vanta warns about. The open-source single-tenant build does not need this program.

## Which incidents are existential for this product, and which controls map to them?

### Takeaway
Three failures end the product: theft of deploy keys, a restore or read that crosses tenants, and a backup that cannot be restored. Encryption with a key stored next to the ciphertext does not stop the first. A confirmation phrase does not stop the second. A checksum without a restore drill does not stop the third. SOC 2 does not prevent any of the three; it is evidence that the controls kept operating.

### Cited Findings
- The worker places the decrypted deploy key in the child environment as `CONVEX_DEPLOY_KEY` for export and for the connection check. Whoever can read that process environment, the master key, or the secret row plus the key can export the customer’s Convex deployment. — [crates/core/src/convex.rs](../../../crates/core/src/convex.rs), [crates/core/src/secrets.rs](../../../crates/core/src/secrets.rs)
- Restore is gated by a typed deployment name and an exact phrase, and by a verification check. There is no tenant match. — [crates/core/src/restore.rs](../../../crates/core/src/restore.rs)
- Manifests record plaintext and stored hashes and stay unencrypted even when the archive is age-encrypted. Verification and restore are specified to decrypt before import. The UI and CLI are supposed to make key-loss consequences explicit. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md)
- Article 32 names the ability to restore availability and access after an incident, and regular testing of security measures, as part of security of processing. — [GDPR Article 32](https://gdpr-info.eu/art-32-gdpr/)
- SC-12 and SC-28(3) are the NIST statements of “manage keys” and “do not leave key material unprotected next to the data.” AC-4 is the information-flow control for data moving between components. — [NIST SC-12](https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-12/), [NIST SC-28](https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-28/)
- OWASP 4.1.6 / 4.3.4 and the multi-tenant cheat sheet are the statements of “an authenticated user must not operate on another tenant’s objects,” including IDOR by substituting an id. — [OWASP ASVS issue 2716](https://github.com/OWASP/ASVS/issues/2716), [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
- ASVS 3.7.1 requires re-authentication or secondary verification before sensitive transactions. — [OWASP ASVS V3](https://github.com/OWASP/ASVS/blob/master/4.0/en/0x12-V3-Session-management.md)
- Audit events today cover a subset of the security-model list: user creation, token creation, secret storage, resource creation, backup start and completion, and restore completion. The security model also lists auth events, role changes, token revocation, secret rotation and deletion, and destructive-restore confirmations as what audit entries should record. — [docs/SECURITY_MODEL.md](../../../docs/SECURITY_MODEL.md)

### Inferences
- **Existential: deploy-key theft.** Impact is silent export of the live Convex database and the ability to impersonate the deployment admin, plus every archive the operator holds. Controls: KMS-wrapped per-tenant data keys and encryption context; master key not in the same backup as the database; short-lived unwrap in the worker only; MFA and re-auth on secret and token actions; CloudTrail or equivalent on decrypt; customer-visible secret-use audit; deploy-key rotation instructions. The self-hosted product already tells the operator they hold the key. The hosted product has to tell the customer the same thing.
- **Existential: cross-tenant read or restore.** Impact is one customer’s production data written into another customer’s Convex deployment, or one agency client’s key used for another client. Controls: tenant predicate plus RLS; restore target constrained to the archive’s tenant; object-storage prefix and credential scope; negative tests that call APIs with another tenant’s ids; break-glass access separated from the request role. The confirmation phrase remains a safety interlock for the rightful operator.
- **Existential: backup that cannot be restored.** Impact is the product failing at the moment it is purchased for. Controls already sketched in the repo: checksum and manifest, decrypt-before-import, verification states, retention that cannot delete the only good copy, and a drill to an alternate deployment. Hosted addition: a scheduled drill whose result is customer-visible, and a documented failure if the age passphrase or KMS key is gone. Article 32’s restore clause is this incident written as a legal duty once the archives contain personal data.
- **Serious but not the same three:** a single tenant filling the queue, an operator laptop with a production bearer token, an unexpired `web-login` token from every historical login, and a support user who is a global admin. Map those to per-tenant quotas, session expiry, token expiry, and audited break-glass. They become existential only if they are the path into one of the three failures above.
- **Minimum honest story before any trust report:** publish the custody model, name the three failures, show the controls that exist, and do not imply a SOC 2 report, a customer-held key, or tenant isolation the schema does not implement. Keep shipping the open-source single-tenant app for people who will not accept operator custody.
